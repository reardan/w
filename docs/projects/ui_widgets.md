# Widget expansion: the `graphics/ui/widgets/` tree

Design assessment for issue #441: *"Expand the current widgets.w into
its own widgets/ sub-folder. Make sure we have: Form; Dropdown
(multi-select dropdown, search); Text box; Textarea; Radio buttons;
Popover; Modal window; Toast; Buttons; Calendar Picker; Date Range
Picker; Time Range Picker; Calendar; Email; Tabs; Chips; Table."*
The maintainer's framing for the issue is that this is *"in preparation
for adding a text editor, and an IDE"* — which is what sets the
priorities below.

Companion to `docs/projects/ui_framework.md` (the framework this builds
on, issue #334, stages 1-4 landed 2026-08-07) and its execution plan
`docs/projects/ui_framework_plan.md`. Same survey → options → staged
recommendation shape.

Status: design 2026-08-09; round 1 implemented 2026-08-09 across
stages 1-8 of `docs/projects/ui_widgets_plan.md` (the execution plan,
which records what each stage actually landed). All four foundation
gaps in §0 are closed and the three proving widgets in §5 ship. The
fourteen deferred items keep the staging in §6, and the open questions
in §8 stand except where round 1 answered them — noted inline there.

## 0. The finding, up front

Almost none of the eighteen items in the issue are blocked on widget
code. Four of them are already shipped and only need extending
(Buttons → `ui_button`, Text box → `ui_textbox`, Radio buttons →
`ui_radio`, Dropdown → `ui_dropdown`). The other fourteen are blocked
on four missing pieces of *foundation* that the nine existing widgets
never needed — and each of those four is also a hard prerequisite for
the text editor the issue is preparing for:

1. **There is no clipping.** `ui_render_quad` (`graphics/ui/render.w`)
   emits geometry unconditionally. Nothing can scroll, nothing can be
   masked to a viewport. Table, Textarea, Tabs and every menu need it.
   `glScissor` has been bound in `graphics/gl.w` since the stage-1
   texture PR and is still unused.
2. **There is one overlay flag and one modal slot.**
   `ui_renderer.to_overlay` is a single `int32` and `ui_context.modal` a
   single widget id. A Popover inside a Modal, or a Toast above both,
   cannot be expressed at all.
3. **There is one vertical stack cursor.** `ui_layout_next` walks a
   single column with a `ui_same_line` escape hatch. Modal bodies,
   toast corners, tab content, table cells and form columns each need
   free placement, which without a general mechanism means a special
   case per widget.
4. **There is no text substrate and no editor keys.**
   `ui_textbox_state` is a fixed `char[128]`. `graphics/event.w` has
   four NAV codes (LEFT/RIGHT/HOME/END) and **no modifier flags at
   all** — no shift, ctrl or alt reaches widget code, so there is no
   selection, no word motion, and no shortcuts. `GFX_EVENT_SCROLL` is
   produced by X11 (`window_x11.w:161`) and by the web host
   (`tools/web/index.html:94`) and then silently ignored by
   `ui_feed_event`.

So the recommendation is to spend the first round on foundation, prove
it with the three widgets that between them exercise all four gaps —
**Modal, Table, Textarea** — and stage the remaining fourteen behind
it. Those three are not an arbitrary sample: they are a dialog, a
list/grid, and an edit surface, which is the minimum an editor needs.

## 1. What exists today

`graphics/ui/` after issue #334's stages 1-4 (PR #428):

| Module | Role |
|---|---|

| `theme.w` | `ui_color`, `ui_theme` (15 color + 7 metric tokens), light/dark/ocean presets |
| `font.w` + `font_data.w` | Baked Liberation Sans atlas (16ppem body, 20ppem bold title) + 7 procedural AA masks; `font_data.w` is generated by `tools/generate_ui_atlas.w` |
| `render.w` | One batching renderer, one shader, one R8 atlas; main batch + a single overlay batch |
| `text.w` | `ui_draw_text`, `ui_draw_text_centered` |
| `widgets.w` | 607 lines: context, layout, and nine widgets |
| `demo_shared.w` / `demo.w` / `demo_web.w` | One form, two drivers (X11 while-loop, wasm frame callback) |

The nine widgets: `ui_label`, `ui_title`, `ui_button`, `ui_textbox`,
`ui_checkbox`, `ui_radio`, `ui_toggle`, `ui_progress`, `ui_dropdown`.

The model is strictly immediate-mode (`ui_framework.md` §3 chose this
deliberately): widgets are function calls made every frame, persistent
state is caller-owned and passed by pointer, ids are sequential in call
order, and an interactive widget returns 1 only on the frame its edge
happens. Nothing here proposes changing that.

Two properties of the existing code are worth stating because the plan
depends on them:

- **`graphics/` is a leaf consumer.** `w.w` does not import it, so
  `./wbuild verify`'s self-host fixpoint and the `SEEDS` pin are not
  implicated and current W syntax is fine throughout.
- **W is single-pass and requires declaration before use** across
  modules (`compiler/symbol_table.w:715`). There can be no import
  cycles, and the order of imports in an umbrella module *is* the
  dependency order. This is what forces the module split in §3.

## 3. Where the code goes

`graphics/ui/widgets.w` becomes a **pure umbrella of imports**, exactly
the `grammar.w` / `codegen.w` pattern — including the single dummy
declaration those files carry (`grammar.w`'s
`int grammar_no_reason_temp_var`), since a file of nothing but imports
needs at least one declaration. Every existing consumer keeps
`import graphics.ui.widgets` unchanged; nothing outside `graphics/ui/`
moves. `grammar.w` + `grammar/` and `repl.w` + `repl/` are the in-tree
precedent that a module file and a same-named directory coexist — the
resolver maps a dotted name straight to `<path>.w`, so
`graphics.ui.widgets` and `graphics.ui.widgets.button` never collide.

Because there can be no cycles, the umbrella's import order is the
dependency order, and the first three modules are forced apart by it:
`ui_begin` (context) resets the layout cursor, so the layout functions
must already be declared, but they operate on fields of `ui_context`,
so the struct must come first.

```
graphics/ui/widgets/state.w      structs only: ui_input, ui_layout, ui_context
graphics/ui/widgets/layout.w     cursor + region stack over ui_context
graphics/ui/widgets/overlay.w    popup scopes + render layers
graphics/ui/widgets/context.w    init / begin / end / feed_event / click_behavior
graphics/ui/widgets/scroll.w     scrollable regions + scrollbars
graphics/ui/widgets/buffer.w     growable multi-line text buffer (pure)
graphics/ui/widgets/basic.w      ui_label, ui_title, ui_button
graphics/ui/widgets/choice.w     ui_checkbox, ui_radio, ui_toggle
graphics/ui/widgets/progress.w   ui_progress
graphics/ui/widgets/textbox.w    ui_textbox_state + ui_textbox
graphics/ui/widgets/dropdown.w   ui_dropdown
graphics/ui/widgets/modal.w      ui_modal_begin / ui_modal_end
graphics/ui/widgets/table.w      ui_table_*
graphics/ui/widgets/textarea.w   ui_textarea_*
```

Later rounds add `popover.w`, `toast.w`, `tabs.w`, `chips.w`, `form.w`,
`email.w`, `calendar.w`, `datetime.w` in the same shape.

Two mechanical notes. `tools/wbuildgen.w`'s `wbg_scan` walks `graphics`
recursively, so tests under `graphics/ui/widgets/` are picked up
automatically — but target names are basename-derived and
`wbg_add_generated` hard-errors on a duplicate, so every new test needs
an explicit `name=graphics_ui_*` directive (the `graphics/ui/core_test.w`
precedent). And `package.wmeta` lists modules explicitly; the new ones
go in it.

## 4. The foundation

### 4.1 Clipping: a CPU clip stack, not `glScissor`

**Recommendation: a clip-rect stack on `ui_renderer`, applied inside
`ui_render_quad`.**

`glScissor` is the obvious first thought and it is the wrong tool here.
The renderer's whole design is one `glBufferData` upload and one
`glDrawArrays` per layer; scissoring would require splitting that into
a draw-call list ordered by clip state, which is a structural change to
the thing every widget draws through. Worse, it does nothing under
`ui_render_init_headless` — the GL-free seam every widget unit test is
built on — so every clip test would need a real display, and the wasm
gate could not cover it.

CPU clipping costs one rect intersection per quad, works identically
headless / on wasm / on every backend, needs no change to the batch
model, and is exactly testable by the pinned vertex counts the existing
tests already use.

- `graphics/ui/rect.w` gains `ui_rect ui_rect_intersect(ui_rect a,
  ui_rect b)` and `int ui_rect_is_empty(ui_rect r)`. These are pure, so
  `core_test.w` covers them on wasm and the 32-bit target too.
- `ui_renderer` gains `ui_rect[8] clip_stack` + `int32 clip_depth`,
  with `ui_clip_push` (intersecting with the current clip, so a child
  can never escape its parent), `ui_clip_pop`, `ui_clip_current`.
- `ui_render_quad` intersects the incoming rect with the current clip.
  A fully-clipped quad pushes **no vertices at all**; a partially
  clipped one lerps `u0..u1` / `v0..v1` by the same fractions it
  trimmed off the rect. The lerp handles reversed ranges (`u0 > u1`,
  which the mask primitives already rely on for mirroring) for free,
  because linear interpolation is direction-agnostic.
- A push past depth 8 keeps the current clip and is dropped — the
  documented fixed-capacity convention already used by
  `ui_context.chars` and the event ring.

**The vertex cap has to move too.** `ui_render_max_verts()` is 8192
(1365 quads) and pushes past it are dropped silently. A table page or a
screen of editor text blows that, and dropping geometry silently is a
bad failure mode for a text editor. The two batches grow by doubling on
overflow through `realloc` (`lib/memory.w` — note it takes the *old*
length), keeping `ui_render_max_verts()` as the initial capacity.
Nothing holds a pointer into a batch across a push, so the realloc is
safe. Growth is the safety net; **virtualization** (§4.4, §5) is the
actual answer to scale.

### 4.2 Layers and popup scopes

Today: `ui_renderer.to_overlay` is one boolean selecting a second
batch, and `ui_context.modal` is one widget id that makes everything
else inert. `ui_dropdown` is the only consumer — two writes at
`widgets.w:556` and `:568`.

Replace both with a stack:

- `ui_renderer` keeps `ui_render_layer_count()` = 3 indexed batches
  (`UI_LAYER_BASE`, `UI_LAYER_POPUP`, `UI_LAYER_TOP`), selected by
  `ui_render_layer(ui_renderer* r, int layer)`. `ui_render_end` draws
  them in order. The clip stack is saved and restored per layer, since
  a popup is not clipped by whatever region opened it.
- `ui_context` replaces `int32 modal` with `int32[4] popup_stack`,
  `int32 popup_depth`, and `int32 scope` — the popup id the widget
  currently being issued sits inside (0 = root).
- `ui_popup_begin(ctx, id, area, layer)` / `ui_popup_end(ctx)` push and
  pop the scope, the renderer layer, the clip, and the layout region
  together.
- `ui_click_behavior` generalizes from "inert unless `ctx.modal` is 0
  or me" to "inert when `popup_depth > 0` and `ctx.scope` is not the
  top of `popup_stack`". That one change is what lets a Popover open
  inside a Modal, and a Toast sit above both.

Dropdown migrates onto this API in the same commit, which is the
migration proof: it is the existing consumer, and its tests
(`widgets_test.w:377`, `:407`) already assert on the overlay batch.

Three layers rather than an arbitrary stack is a deliberate call:
base / popup / topmost covers dropdown-in-modal and toast-over-
everything, and an unbounded layer count would mean sorting batches at
end-of-frame for no use case anyone has named.

### 4.3 Layout regions

Replace the flat cursor fields on `ui_context` with a small stack, so
free placement is the general mechanism rather than a per-widget
special case:

```
struct ui_layout:
	ui_rect bounds
	float32 cursor_x, cursor_y, origin_x
	float32 last_right, last_top
	float32 content_w, content_h    # measured extent, for scrolling
	int32 pending_same_line
```

`ui_context` carries `ui_layout[8] layout_stack` + `int32 layout_depth`;
`ui_layout_next` and `ui_same_line` operate on the top of it, and
`ui_begin` seeds depth 0 with the window rect — so today's behavior is
the depth-0 case and nothing existing changes.

`ui_region_push(ctx, area)` starts a fresh cursor at `area`'s origin
plus `theme.pad`; `ui_region_pop(ctx)` restores the parent and folds
the child's measured extent into the parent's `content_*`;
`ui_region_content(ctx)` reports the extent widgets actually occupied,
which is what a scroll region needs to size its bar.

Modal bodies, toast corners, popover bodies, tab content, table cells,
form columns and chip rows are then all the same three lines.

### 4.4 Scroll

`ui_feed_event` finally consumes `GFX_EVENT_SCROLL`. `ui_input` gains
`scroll_x` / `scroll_y` (per-frame accumulated notches, cleared in
`ui_end` like the mouse edges) and `mods`, plus parallel
`int32[32] char_mods` / `int32[8] nav_mods` alongside the existing
`chars` / `navs` queues so a widget can tell shift-Left from Left.

```
struct ui_scroll_state:
	float32 offset_x, offset_y
	float32 content_w, content_h    # from the previous frame's extent
	float32 view_w, view_h

void ui_scroll_begin(ui_context* ctx, ui_rect area, ui_scroll_state* st)
void ui_scroll_end(ui_context* ctx, ui_scroll_state* st)
```

`begin` pushes a clip and a region offset by `-offset_*`; `end` pops
both, records the content extent, claims the frame's wheel delta if the
pointer is inside `area`, clamps the offset, and draws a thin rounded
scrollbar (`ui_draw_rrect`) when content overflows. Dragging the thumb
reuses `ui_click_behavior`'s existing active-id tracking rather than
inventing a drag model.

Content extent lags by one frame, which is the standard immediate-mode
trade and is invisible at 60fps. It is documented rather than hidden.

### 4.5 The text buffer

`graphics/` uses no built-in `list`/`map` and no `structures/`
containers anywhere today — it is `malloc` plus fixed arrays
throughout. Keeping that is not just consistency: a hand-rolled buffer
is unambiguously wasm-safe and keeps the module *pure* (no
`graphics.gl` import), so its test runs on wasm and the 32-bit target
alongside `core_test.w`.

```
struct ui_text_buffer:
	char* data              # NUL-terminated, malloc'd
	int32 length, capacity
	int32* line_starts      # byte offset of each line's first char
	int32 line_count, line_capacity
```

with init/free/set, `insert` (char), `insert_text`, `delete(offset,
count)`, and the line-index queries `line_start`, `line_length`,
`offset_to_line`, `line_col_to_offset`. Growth by doubling through
`realloc`.

The line index is rebuilt on edit, O(n). That is the right first
version — it is obviously correct, and a Textarea holding a source file
still re-indexes in microseconds. Making it incremental is explicitly
the editor's follow-up and is stated in the module header rather than
left as a surprise.

One gotcha to encode in the code: `T* + int` is a raw **byte** offset
for every pointee width, so `line_starts + n` is wrong. Use
`&line_starts[n]` (or `lib/ptr.w`'s `ptr_add`), exactly as
`lib/sha256.w` does.

`ui_textbox_state` stays a fixed `char[128]`. That is right for a
single-line field, and rebasing it on the buffer would churn the
existing textbox tests for no gain.

### 4.6 Editor keys: modifiers and the missing NAV codes

This is the one piece that touches already-shipped, tested code, and
following the #334 precedent (that doc's open question 2, answered
"yes" for the event queue itself) it lands as its own commit against
`graphics/` ahead of the UI work — it benefits any future non-UI
consumer of `gfx_window` too.

- `enum gfx_mod`: `GFX_MOD_SHIFT = 1`, `GFX_MOD_CTRL = 2`,
  `GFX_MOD_ALT = 4`, `GFX_MOD_SUPER = 8`. Bit flags, all far below bit
  31 — hex literals with bit 31 set sign-extend into the word-sized
  `int` on every target.
- `struct gfx_event` gains `int32 mods`.
- `enum gfx_nav_code` gains `UP = 5`, `DOWN = 6`, `PAGE_UP = 7`,
  `PAGE_DOWN = 8`, `DELETE = 9`.
- The ring stride goes 4 → 5 int32s per slot. Capacity stays 64, so the
  `& 63` index masks in `gfx_event_ring_push` / `_next` are untouched
  and only `gfx_event_ring_ints()` changes (256 → 320).

Per backend: X11 already carries the modifier mask in
`x_input_event.state` (`graphics/x11.w:110`) and simply never reads it;
the web host reads `e.shiftKey/ctrlKey/altKey/metaKey` and grows
`pushEvent` plus `gfx_host_next_event`'s `DataView` write by one field;
Cocoa reads `modifierFlags` on the key path it already decodes (mouse
and CHAR stay the documented v1 gap); the stub backend changes only in
struct width.

The frozen-wasm-struct rule does *not* bite here: what is frozen is
`gfx_window` (written by JS at hardcoded byte offsets), not the event
out-buffer. But the two JS hosts and `tools/web/index.html` must change
in lockstep with `window_web.w` or the wasm gates break.

### 4.7 Civil-date math belongs in `lib/time.w`

`lib/time.w` has `time_is_leap_year`, `time_days_in_month`,
`time_days_in_year` and `time_utc_from_unix` — but **no inverse**. A
calendar grid needs "what weekday does the 1st of this month fall on",
which needs y/m/d → days-since-epoch. That is general date arithmetic,
not UI code, so it goes in `lib/time.w` with its own test rather than
being copied into a widget:

```
int time_days_from_civil(int year, int month, int day)
int time_unix_from_utc(date_time* dt)
int time_weekday_from_civil(int year, int month, int day)
```

Calendar is then a month grid over those; Calendar Picker is that grid
inside a popover attached to a date field; Date Range is two anchors
over one grid; Time Range is two spinners in a popover.

## 5. The three proving widgets

Chosen because between them they exercise all of §4 and because they
are the editor's own prerequisites — a dialog, a list/grid, an edit
surface.

**Modal** (`ui_modal_begin(ctx, title, w, h, open) -> int` /
`ui_modal_end(ctx)`) proves layers, regions and popup scope. Returns 1
while open so the caller issues body widgets between the calls; scrim
over the window on `UI_LAYER_POPUP`, centered elevated surface, title
row and close affordance; Escape (already delivered as `CHAR 27`) and a
scrim click close it. `open` is caller state, like the dropdown's flag.

**Table** proves clipping, scroll and regions, and answers the vertex
budget by construction: `ui_table_row` returns 0 for rows outside the
viewport so the caller skips their cells entirely. **Row
virtualization**, not a bigger batch, is what keeps a ten-thousand-row
table cheap. Sticky header outside the scroll clip, zebra body rows
inside it, row selection through the existing click behavior.

**Textarea** proves the buffer and the new nav/modifier events, and is
literally the editor's edit surface: caller-owned
`ui_textarea_state` (buffer, caret line/col, goal column, selection
anchor, scroll state), focus through `ctx.focus` exactly as
`ui_textbox` does, CHAR + the new UP/DOWN/PAGE/DELETE nav codes,
shift-modified nav extending the selection, ctrl+HOME/END for
buffer ends. Draws only the visible line range — the same
virtualization idea as the table — with a selection highlight behind
the glyph runs. Horizontal placement reuses the existing
`ui_text_prefix_width` and `ui_text_caret_from_x`.

## 7. Non-goals for this round

- **Clipboard (ctrl-C/V).** No platform clipboard binding exists on any
  backend, and X11 selections, `NSPasteboard` and the asynchronous
  browser Clipboard API are three genuinely different designs. Its own
  note, before the editor.
- **Cocoa mouse and CHAR.** A pre-existing documented v1 gap
  (`window_cocoa.w:17`) needing a struct-return-free selector strategy.
  The new widgets are compile-verified on `arm64_darwin` through
  `graphics_darwin` but are not interactively usable there.
- **Retained mode / a scene graph.** `ui_framework.md` §3 stages this
  as a post-v1 evolution to revisit with real usage data. Row and line
  virtualization are the cheaper answer to the scale problem that would
  otherwise motivate it.
- **Undo/redo, syntax highlighting, multiple cursors.** Editor
  features, not widget features — they belong to the editor project
  built on this, and the buffer is designed not to preclude them.
- **UTF-8 shaping in the text layer.** Still the #379 typography
  follow-up; the buffer stores bytes and the caret is a byte index,
  matching `ui_textbox` today.

## 8. Open questions for the maintainer

Round 1 answered two of these in passing, noted where they appear
below: the popup mechanism gained an explicit layer argument rather
than an elevation token (question 1 stays open for the *visual* token
set), and Table takes explicit `int32*` column widths rather than a
sizing policy (question 2 stays open for a policy on top of them).

1. **Elevation tokens.** Three layers currently share one `shadow`
   token. Should the theme grow `shadow_low` / `shadow_high` so a
   modal reads as further off the surface than a dropdown, or is one
   shadow enough for "minimal"?
2. **Table column model.** The proposal takes `int32* col_widths` —
   fixed pixel widths, caller-owned. Is proportional/flex sizing wanted
   before Tabs and Form arrive with the same question, or is fixed
   right for a first version?
3. **Toast timing.** Toasts need a clock. Frame counting is
   dependency-free but wrong under a variable frame rate;
   `time_monotonic_ms()` is correct but is a syscall the wasm backend
   would need an equivalent for. Preference?
4. **Editor buffer ownership.** `ui_text_buffer` is proposed inside
   `graphics/ui/widgets/`. If the editor will want it without the
   widget layer (headless file processing, tests), it may belong in
   `lib/` instead. It is pure and has no graphics dependency either
   way — this is a placement call, not a technical one.
