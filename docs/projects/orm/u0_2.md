# U0.2: streaming SQL cursor

Part of the w-orm plan (issue #754). Adds a cursor API to
`libs.standard.sql.client` so scans (`iterator()`, history backfills) are not
bound by the result collector's 100,000-row / ~64 MiB limits.

## API

```w
sql_cursor* sql_query_cursor(sql_connection* c, char* query, int count, char** params)
int sql_cursor_next(sql_cursor* cur)          # 1 row, 0 end, -1 error (sql_error(c))
int sql_cursor_columns(sql_cursor* cur)
char* sql_cursor_column_name(sql_cursor* cur, int col)   # borrowed until free
char* sql_cursor_value(sql_cursor* cur, int col)         # borrowed until next/free
int sql_cursor_value_length(sql_cursor* cur, int col)    # -1 NULL, -2 no row/bad col
void sql_cursor_free(sql_cursor* cur)
```

Typical loop:

```w
sql_cursor* cur = sql_query_cursor(db, c"SELECT id FROM t", 0, cast(char**, 0))
if (cur == 0): return fail(sql_error(db))
int rc = sql_cursor_next(cur)
while (rc == 1):
	use(sql_cursor_value(cur, 0))
	rc = sql_cursor_next(cur)
sql_cursor_free(cur)
if (rc < 0): return fail(sql_error(db))
```

## Decisions

- **SQLite**: `sqlite3_prepare_v2` + `sqlite3_step`, sharing
  `sql_sqlite_prepare` (single-statement check, native binding) with
  `sql_query`. Values are read on demand with `sqlite3_column_text`, which
  keeps BLOB bytes (embedded NULs) and NUL-terminates; empty values return a
  non-null `""`.
- **PostgreSQL**: `PQsendQueryParams` + `PQsetSingleRowMode` + `PQgetResult`.
  The first result is fetched in `sql_query_cursor`, so syntax/missing-column
  errors return 0 there and column names are known before the first row
  (also for zero-row results).
- **Connection lock**: `sql_connection.cursor` holds the open cursor (as an
  `int`, since W has no forward struct references). `sql_query_params`,
  `sql_query_cursor`, `sql_begin` and `sql_end_transaction` fail with
  "sql: connection has an open cursor; free it first" while it is set. The
  lock is released as soon as `sql_cursor_next` returns 0 or -1 (the native
  statement is finished then), or on `sql_cursor_free`.
- **Early free on PostgreSQL**: outside a transaction (`PQtransactionStatus`
  idle when the cursor opened) the query is cancelled with `PQcancel`, then
  results are drained; inside a transaction it only drains, because a cancel
  would abort the transaction. The test proves the cancel path skips a 20 s
  `pg_sleep` tail.
- **`sql_close` with an open cursor** finalizes/clears its native state
  without draining and detaches it; the cursor then returns -1 from
  `sql_cursor_next` and must still be freed.
- MySQL, SQL Server and Oracle return 0 with
  "sql: cursors are only implemented for SQLite and PostgreSQL".

## Limits

- One open cursor per connection; no other queries meanwhile (SQLite could
  interleave statements, but both drivers follow the same rule).
- Only the 1,024-column limit applies; no per-cell or total-size limit.
- PostgreSQL reports errors that happen partway through after the rows sent
  so far; SQLite reports statement errors at `sql_cursor_next`.
- An early free inside a PostgreSQL transaction reads (and discards) the
  remaining rows.
- COPY through a cursor closes the connection, as `sql_query` does.

## Tests

- `sql_cursor_test` (SQLite): 150,000 rows from a recursive CTE, NULL / empty /
  binary values, parameters, lock errors, early free, transactions,
  mid-stream error, close with an open cursor, unsupported driver.
- `sql_cursor_postgres_local_test` (PostgreSQL via
  `bin/sql_postgres_fixture` (tests/sql_postgres_fixture.w), needs a non-root user): the same with
  `generate_series`, plus cancel timing, drain-in-transaction and COPY.
