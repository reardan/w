# H1: hardening pass

Part of w-orm ([#754](https://github.com/reardan/w/issues/754),
[orm.md](../orm.md)). Fixes for problems the unit agents reported, each
with a test. The admin (`admin/`) and web (`web/`) directories are
untouched.

## What landed

| # | Problem | Fix | Test |
| --- | --- | --- | --- |
| 1 | SQLite reused a deleted row's id, so a new object inherited the deleted one's history. | Auto pks (models and M2M through tables) are `INTEGER PRIMARY KEY AUTOINCREMENT`. The 12-step rebuild and SWAP_TABLES carry the `sqlite_sequence` high-water mark to the new table; on PostgreSQL the DROP_SYNC_TRIGGER that ends a table rebuild moves both tables' sequences past the shared sequence's last id. The example's history-by-reason lookup is gone. | `orm_apply_*`: a deleted newest book across a SQLite rebuild and a deleted author across the swap keep their ids; `orm_example_test` reads the oldest history row. |
| 2 | A NOT NULL rename's migrate step added `CHECK (c IS NOT NULL) NOT VALID`, which on SQLite rejected old-code inserts. | Contract: `orm_op.dialects` (0 = all, else `ORM_OP_ON_SQLITE` / `ORM_OP_ON_POSTGRES`), `orm_op_runs_on`. The planner masks the CHECK, VALIDATE and DROP_CONSTRAINT of NOT NULL tightening to PostgreSQL; the applier skips (dry run: comments) and the linter ignores ops for other dialects; the writer and `orm_plan_describe` (`postgres_only`) carry the mask; unapply keeps it. | `orm_apply_*`: the title -> name rename is planned for PostgreSQL and applied on both dialects, with an old-code insert after the migrate step; `orm_migrate_lint_test`, `orm_migrate_writer_test`, `orm_planner_test`. |
| 3 | SQLite fires the newest trigger first, so a rename's dual-write `~` row came before the insert's `+` row. | The history triggers are reinstalled after a column SYNC_TRIGGER (`orm_hist_after_sync_columns`), and the 12-step rebuild recreates `w_hist_*` triggers last. | `orm_apply_*`: the oldest history row of an old-code insert is `+`. |
| 4 | A fresh database needed `--force` for a full list. | `requires_applied` pointing earlier in the same run is accepted when no migration of the app is recorded. `orm_migrate_upto(ms, name)` and `migrate apply --upto <name>`. | `orm_cli_test` (`--upto`, unknown name), `orm_example_cli_test` (`--upto` then the rest; a fresh file takes all 7 without `--force`). `orm_example_test` still sees the refusal once release 1 is recorded. |
| 5 | `session.orm` could not FK to auth's User; history wrapper names were not reserved. | `.orm` `import <path>`: an imported file's models are FK targets (typed slot, import of its data module, its `<app>_register()` first). Session `user` is a nullable FK (NULL = anonymous), ApiToken `user` an FK, both `on_delete=cascade`; the committed modules and the example's `session.0001_initial` are regenerated. Relations and `related_name`s named `history`, `as_of`, `history_row`, `prune_history` are refused on history models. | `orm_schema_test` (imports, every new error), `orm_session_test` (FK descriptors, NULL anonymous user, user delete cascades), `orm_session_gen_test`, `orm_auth_gen_test`, `orm_example_*`. |
| 6 | Prefetch to_attr lists lived among row-meta annotations as `prefetch:<name>`. | `orm_row_meta.attr_names` / `attr_values` (load.w) hold them; `orm_row_prefetched` reads them. The serializer keeps refusing `prefetch:` annotation names as a guard. | `orm_related_test`: next to an annotation, the row has one annotation and one attr, and no annotation answers to the to_attr name. |

## Decisions

- Option (a) for item 2: an explicit mask in the contract rather than a
  SQLite applier rule keyed on constraint names, so a hand-written op can
  use it too and the linter agrees with the applier.
- The planner still plans per dialect (a SQLite plan has no CHECK ops);
  the point is that a PostgreSQL plan, the committed superset, applies
  on SQLite unchanged.
- "Fresh" is per app: once any migration of the app is recorded, old
  code may be running and the expand/contract rule holds again.
- `import` paths resolve like W imports (from the repository root) and
  fall back to the importing file's directory; the data module name is
  derived from that path and the imported file's `app`.
- `auth_session.user_id` (the runtime struct) keeps 0 for anonymous; only
  the row stores NULL.

## Limits

- Only FKs cross files: no M2M and no `related_name` to an imported
  model (its module is generated separately).
- Migrations do not record a dependency on the target app's migrations;
  the target app must come first in the list (it does in the example).
- The schema snapshot names the target by `rel_model` only.
