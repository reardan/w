# U2.1: relations and transactions

Part of w-orm ([#754](https://github.com/reardan/w/issues/754),
[orm.md](../orm.md)), plan sections 4.3 and 4.5. This unit adds
prefetch_related execution, explicit relation loaders, streaming
`iterator()` and transactions (`orm_atomic`, savepoints, `on_commit`).

## What landed

| File | What |
| --- | --- |
| `libs/standard/orm/related.w` | Prefetch executor, `Prefetch` objects, to_attr storage, `orm_prefetch_related_objects`, `orm_load_related`, `orm_iterator` / `each`. |
| `libs/standard/orm/atomic.w` | `orm_atomic`, begin/commit/rollback blocks over `sql_begin` and U0.3 savepoints, `orm_on_commit`, rollback-only. |
| `libs/standard/orm/query.w` | Small marked hooks: a forward declaration of `orm_prefetch_execute`, `orm_with_prefetch` called by `all()`, `first()` and `get()`, and `import libs.standard.orm.related` at the end of the file. Importing `orm.w` or `query.w` therefore brings in all of U2.1. |
| `tests/orm/orm_related_cases.w`, `orm_atomic_cases.w` | Scenarios shared by SQLite and PostgreSQL. Every evaluation asserts the exact statement count. |

Tests: `orm_related_test` and `orm_atomic_test` (SQLite in memory),
`orm_relations_postgres_test` / `orm_relations_postgres_local_test` (both
scenario sets on a temporary cluster via `tests/sql_postgres_fixture.py`,
plus an aborted-savepoint case and `select_for_update(skip_locked)` across
two connections).

## Decisions

- **One query per hop.** A path like `books__tags` runs one query per hop
  and batch: `SELECT ... WHERE key IN (?, ...)` over the distinct keys of
  the rows loaded so far. A batch holds at most `max_params - 100` keys
  (899 on SQLite), so a custom queryset keeps room for its own values.
  Queries for a hop are ordered by the target pk unless the Prefetch
  queryset orders them.
  - Forward FK: `pk IN (<fk ids>)`, stored in the FK pointer slot. Rows
    whose slot select_related already filled are skipped, so a hop where
    every slot is filled runs no query.
  - Reverse FK: `<fk> IN (<parent pks>)`. Each child's FK pointer is set to
    its parent, so `book.author` works after `prefetch_related("books")`.
  - M2M: one query joining the through table. The hop queries a private
    copy of the target descriptor with an extra reverse relation
    `_prefetch_link` to a private through-table descriptor, so U1.2's
    compiler emits
    `SELECT t0.*, t1.book_id AS "_prefetch_key" FROM library_tag t0 LEFT JOIN library_book_tags t1 ON t1.tag_id = t0.id WHERE t1.book_id IN (...)`.
    A tag linked to two books loads as two row objects. The rows carry the
    `_prefetch_key` annotation.
- **Shared prefixes run once.** Within one evaluation, a default-slot hop
  is not run again: `prefetch_related("books")` followed by
  `"books__tags"` makes 3 queries. A Prefetch queryset or a `to_attr`
  applies to the **last** hop of its path only. Earlier hops use default
  slots, as in Django.
- **Ownership (C6).** Hop rows load into a temporary result whose memory is
  moved into the evaluated result (`orm_result_adopt`), so
  `orm_result_free` frees everything. The relation lists of result rows
  are result-owned. A slot that is filled again is cleared first.
  `orm_prefetch_related_objects` and `orm_load_related` return a **new**
  `orm_result` that owns the loaded rows (its `rows` list is empty), for
  rows from any result or from `orm_row_new`. Free it only when you no
  longer need the slots it filled: freeing it leaves those slots dangling.
- **to_attr storage.** A to_attr list is a `list[void*]` stored in the row
  meta annotations (load.w) under the name `prefetch:<to_attr>`. The value
  is the list pointer, not text. Read it with `orm_row_prefetched`. Names
  in the shared annotation list are copied on write, once per distinct
  source list. Serializers must skip annotation names that start with
  `prefetch:`. On a forward FK, to_attr holds a list of 0 or 1 rows.
  to_attr on heap rows allocates their annotation lists in the returned
  owner result.
- **Prefetch querysets** must be over the hop's model, unsliced, and not in
  values() mode. Their `select_related` joins inside the hop query. Their
  own `prefetch_related` runs on the hop's rows (nested Prefetch).
- **Explicit loaders always query.** `orm_load_related` reloads even a
  filled slot (one query; none for a NULL FK). This makes N+1 patterns
  show up in query counts.
- **iterator()** compiles the query once, opens `sql_query_cursor` (counted
  as one statement), and loads `chunk_size` rows (default 2000) at a time
  into a chunk `orm_result` through the same loaders as `all()`. A row
  stays valid until the next chunk is read; then the previous chunk is
  freed. values()/values_list() rows stream as well. Because the cursor
  holds the connection, `prefetch_related` on an iterated queryset is an
  error. Use `orm_prefetch_related_objects` per chunk after the cursor is
  done.
- **Transactions.** The outermost block is `sql_begin` / `sql_commit`, and
  nested blocks use savepoints `w_sp_<depth>` with a depth counter in
  `db.atomic_depth`. BEGIN, COMMIT, ROLLBACK, SAVEPOINT, RELEASE and
  ROLLBACK TO each count as one statement in `db.query_count`, as in
  Django's assertNumQueries. When a block's function returns 0, the block
  rolls back (ROLLBACK, or ROLLBACK TO + RELEASE), keeps the function's
  error text and returns 0. The enclosing function **propagates** that
  failure by returning 0 itself, or carries on. When a RELEASE fails (on
  PostgreSQL, a statement in the block failed and aborted the transaction,
  but the function still returned 1), the block rolls back to its
  savepoint, which leaves the transaction usable, and returns 0.
- **rollback_only.** `orm_set_rollback(db, 1)` dooms the innermost open
  block. When that block ends, it rolls back even if its function
  returned 1, returns 0 with "orm: transaction was marked rollback-only",
  and clears the flag. A failed ROLLBACK TO also sets the flag, so the
  enclosing block rolls back too.
- **on_commit.** Callbacks run in order after the outermost COMMIT
  succeeds. Callbacks queued inside a block that rolls back (savepoint or
  whole transaction) are discarded with it. Outside a transaction a
  callback runs at once. Blocks must end in reverse order. Ending them out
  of order fails with "atomic blocks must end in reverse order".
- **select_for_update** keeps U1.3's check: SQLite fails before compiling
  with "orm: select_for_update is not supported by this database". On
  PostgreSQL, `for_update(1, 0)` (SKIP LOCKED) and `for_update(0, 1)`
  (NOWAIT) are tested across two connections. Using it outside a
  transaction is not rejected, because U1.3's e2e test relies on that.

## Limits

- No query result caching. Each evaluation of a queryset with prefetches
  runs all its hops again.
- Reverse M2M (from Tag to its books) is not a descriptor field yet, so it
  cannot be prefetched.
- Prefetching an M2M from a custom queryset that aggregates would group by
  the `_prefetch_key` column as well. This combination is untested.
- `get_or_create`'s retry still runs without a savepoint. Inside a
  PostgreSQL transaction, wrap the call in `orm_atomic` so a unique-race
  INSERT failure can be rolled back. A follow-up should take that
  savepoint inside write.w.
