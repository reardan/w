# U0.3: SQL savepoints

Part of the w-orm plan (issue #754, docs/projects/orm.md). Nested
transactions for `orm_atomic`, layered on the existing
`sql_begin`/`sql_commit`/`sql_rollback` in `libs/standard/sql/client.w`.

## What landed

- `libs/standard/sql/savepoint.w` (imports `client`; no changes to the
  client itself).
- `sql_savepoint_test` (SQLite, in memory) and
  `sql_savepoint_postgres_local_test` (temporary PostgreSQL cluster via
  `tests/sql_postgres_fixture.py`; the binary target
  `sql_savepoint_postgres_test` prints SKIP without `W_SQL_POSTGRES`).

## API

```w
int sql_savepoint(sql_connection* c, char* name)              # SAVEPOINT "name"
int sql_release_savepoint(sql_connection* c, char* name)      # RELEASE SAVEPOINT "name"
int sql_rollback_to_savepoint(sql_connection* c, char* name)  # ROLLBACK TO SAVEPOINT "name"
char* sql_savepoint_name(int depth)     # malloc'd "w_sp_<depth>"; 0 if depth < 0
int sql_savepoint_name_valid(char* name)
```

All three operations return 1/0 and report through `sql_error(c)`,
which is cleared on entry.

## Decisions

- **Validation before SQL.** Names must be 1..63 bytes of ASCII
  letters, digits and `_`, not starting with a digit (63 is
  PostgreSQL's identifier limit). They are always emitted double-quoted,
  so case is preserved and keywords are safe. Nothing user-controlled
  reaches the SQL text unvalidated.
- **Only inside `sql_begin`.** `c.transaction == 0` is an error rather
  than letting SQLite open an implicit transaction with `SAVEPOINT`;
  that would leave `c.transaction` out of sync with the database.
- **SQLite and PostgreSQL only.** Other drivers fail with
  `sql: savepoints are not supported for this client` before any I/O.
- **No savepoint stack in the connection.** The database tracks the
  stack; the wrapper is stateless. Database semantics apply unchanged:
  `ROLLBACK TO` keeps the savepoint open and discards everything opened
  after it; `RELEASE` also releases inner savepoints, and released work
  still belongs to the enclosing level.
- **PostgreSQL recovery.** After a failed statement the transaction is
  aborted; `sql_rollback_to_savepoint` to a savepoint taken before the
  failure clears that state (tested). This is what `orm_atomic` relies
  on for an inner block that fails.

## Limits / notes for the ORM

- An unknown savepoint name is a server error; on PostgreSQL that
  aborts the transaction, and `sql_commit` then reports the abort.
- `orm_atomic` should use `sql_savepoint_name(depth)` and keep its own
  depth counter; the SQL layer does not.
