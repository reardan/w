# U3.1: users, groups, permissions, passwords

Part of w-orm ([#754](https://github.com/reardan/w/issues/754),
[orm.md](../orm.md)). Django's `contrib.auth` core over the generated
auth models: Django-compatible password hashes, users and
authentication, groups, model and object permissions.

## What landed

## Schema (Django-shared)

| Model | Table | Columns |
| --- | --- | --- |
| ContentType | `django_content_type` | id, app_label(100), model(100); unique (app_label, model) |
| Permission | `auth_permission` | id, name(255), content_type_id, codename(100); unique (content_type_id, codename) |
| Group | `auth_group` | id, name(150) unique |
| User | `auth_user` | id, password(128), last_login null, is_superuser, username(150) unique, first_name(150), last_name(150), email(254), is_staff, is_active, date_joined |
| M2M | `auth_group_permissions` (group_id, permission_id), `auth_user_groups` (user_id, group_id), `auth_user_user_permissions` (user_id, permission_id) | |

Permission keeps Django's `content_type` FK rather than a model-label
column, because the brief's goal was sharing a Django database and
Django's `auth_permission` has no label column; the label is
`content_type.app_label` + `codename`. The bools and the three name/email
columns carry database defaults (`FALSE`/`TRUE`/`''`) that Django does not
declare; this is harmless to Django. `last_login` / `date_joined` are
`TIMESTAMP` (no time zone) on PostgreSQL, matching the rest of w-orm's
text-UTC datetimes; Django with `USE_TZ` uses `timestamptz`, which reads
back with a `+00` suffix but still compares correctly.

## API

Passwords (`password.w`):

- `make_password(raw)` -> owned `pbkdf2_sha256$<iter>$<salt>$<b64>`; raw 0
  gives an unusable `!` + 40 random characters.
- `make_password_with(raw, salt, iterations)` (0 = random / current).
- `check_password(raw, encoded)`: recomputes and compares the whole encoded
  text with `secrets_compare_digest` (constant-time). Unusable, malformed
  or non-`pbkdf2_sha256` values never match.
- `password_needs_rehash(encoded)`: another algorithm, iterations **below**
  the current setting, or a salt shorter than 22 characters (Django's
  128-bit salt rule). Lowering the setting does not trigger rehashes.
- `is_password_usable`, `auth_password_decode` / `auth_password_parts`.
- `auth_password_set_iterations(n)` (0 = default 1,000,000, Django 5.2's),
  `auth_password_iterations()`. One 1M-iteration hash takes about 1.2 s on
  the x64 build; tests use 1000.
- Salts: 22 characters of `[A-Za-z0-9]` from `secrets_randbelow`, as
  Django's `get_random_string`.

Users (`user.w`); every `User*` returned is a heap row freed with
`User_free`:

- `create_user(db, username, email, password)` /
  `create_superuser(...)`: one INSERT. Email domain lower-cased
  (`auth_normalize_email`); email 0 takes the database default `''`;
  `is_active` is set to 1 explicitly (an int field's database default is
  never used by `save`, see U1.3).
- `user_get(db, id)`, `user_get_by_username(db, name)` (case-sensitive).
- `set_password(u, raw)` (no save), `set_unusable_password`,
  `user_has_usable_password`, `user_check_password(db, u, raw)` (saves an
  upgraded hash), `user_is_active`, `user_can_authenticate`.
- `authenticate(db, username, password)`: one SELECT, then one UPDATE that
  writes `last_login` and, when `password_needs_rehash`, the new hash.
  Unknown users still run one hash (Django's timing mitigation). Inactive
  users are refused but their stale hash is still upgraded (Django's
  order). All refusals set `AUTH_INVALID_LOGIN()` in `orm_db_error`.

Permissions (`perms.w`), perms named `"app_label.codename"`:

- `user_has_perm(db, u, perm)`, `user_has_perms(db, u, list)`,
  `user_has_module_perms(db, u, app)`, `user_get_all_permissions(db, u)`
  (new list of new strings; `auth_perm_list_free`). Inactive users: none,
  no query. Active superusers: `has_perm` is 1 with no query;
  `get_all_permissions` lists every Permission row (as Django).
- Cache: the first check per user loads the user's and their groups'
  permissions (2 queries: values_list over the two M2M paths) into a map
  keyed by user id; later checks run nothing. Entries are tied to the
  `orm_db` pointer and the user's `is_superuser`, and invalidated by
  `user_add/remove_permission`, `user_add/remove_group` (that user) and
  `group_add/remove_permission`, `orm_auth_create_model_permissions*`
  (everyone, via a generation counter). Changes made any other way (raw
  SQL, `orm_m2m_*` directly, another process) need
  `auth_perm_cache_invalidate_user(id)` or `auth_perm_cache_clear()`.
- `group_get_or_create(db, name)`, `permission_get(db, "app.codename")`
  (heap rows).
- `orm_auth_create_model_permissions(db, m)`: get-or-create the content
  type (`app_label`, model name lower-case), then one
  `INSERT ... ON CONFLICT DO NOTHING` of `add_/change_/delete_/view_<model>`
  named `Can add <verbose name>` (Django's `camel_case_to_spaces`).
  Returns permissions created. The app label is the table prefix
  (`library_book` -> `library`); models whose `table=` does not follow
  `<app>_<model>` use `orm_auth_create_model_permissions_app(db, app, m)`.
  `orm_auth_create_auth_permissions(db)` creates Django's 16 for
  `contenttypes` and `auth`.
- Object permissions: `type auth_obj_perm_fn = fn(orm_db*, void* user,
  char* perm, orm_model_desc*, void* obj) -> int`;
  `auth_register_object_permission(fn)`, `auth_clear_object_permissions()`;
  `user_has_obj_perm(db, u, perm, m, obj)` (obj 0 = `user_has_perm`).
  Hooks run in order: > 0 grants, < 0 denies and stops (Django's
  `PermissionDenied`), 0 abstains. Active superusers pass without hooks;
  inactive users fail. Model permissions do not imply object permissions
  (Django's ModelBackend).

## Generated modules

`tools/orm_gen.w` owns the `orm_generated` target and its inputs, so
`auth.orm` is not generated at build time. Instead the three outputs are
committed next to it, made with

```sh
bin/orm_gen libs/standard/orm/auth/auth.orm -o libs/standard/orm/auth/auth
```

and `orm_auth_gen_test` (declared in `orm_auth_test.w`) regenerates them
into `bin/orm_auth_gen/` and `cmp`s each file, so a change to `auth.orm`
or to the generator that is not re-run fails the suite. Moving `auth.orm`
into `orm_generated` later only needs the generator's header lines.

## Limits

- Tables come from hand DDL in tests until U2.4's applier lands; then the
  tests should create them from `auth_schema_json()`.
- Only `pbkdf2_sha256` verifies. Django's other hashers (argon2, bcrypt,
  scrypt, `pbkdf2_sha1`) are reported as `password_needs_rehash` but cannot
  log in.
- Username comparison is exact; no Unicode normalization (Django applies
  NFKC in `AbstractBaseUser.clean`, not in `authenticate`).
- The cache is process-global and unbounded (one entry per checked user);
  web units should clear it per request if they want Django's per-request
  semantics.
