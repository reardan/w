# U2.2: migration state, autodetector, writer

Part of w-orm (issue #754, plan section 5.1). Consumes contract C7
(`orm_op`, `orm_migration`), the U1.1 schema snapshot
([u1_1.md](u1_1.md)) and the U2.3 planner ([u2_3.md](u2_3.md)). No SQL
is generated or run here.

## API

```
orm_state* st = orm_state_from_migrations(c"library", migrations)  # st.error on a bad op
char* json = orm_state_to_json(st)
orm_state_apply_op / orm_state_apply_migration / orm_state_from_json / orm_state_expand_snapshot

orm_detect* d = orm_autodetect(old_state_json, library_schema_json(), hints)  # d.changes, d.error
char* text = orm_detect_describe(d)

orm_makemig* r = orm_makemigrations(c"library", old_state_json, snapshot, ORM_DIALECT_POSTGRES, next_number, previous, hints)
orm_makemig* r = orm_makemigrations_next(c"library", existing_migrations, snapshot, dialect, hints)
# r.migrations, r.error; orm_makemig_free(r)

orm_write_migrations(c"app/migrations", c"app.migrations", c"library", migrations, &error)  # -> modules written
```

`orm_autodetect` returns a struct (`changes`, `error`) rather than a bare
list so it can own its strings and report bad hints; `orm_makemigrations`
takes the dialect and the previous migration name too, because the
planner's sequences differ per dialect.

## State

The state is the U1.1 snapshot object (`format`, `version`, `app`,
`models`); every model and field is normalized to the snapshot's full key
set in its key order (missing keys get defaults), so replaying an
initial migration gives exactly `orm_state_expand_snapshot(snapshot)`.
Two differences from a generator snapshot:

- **M2M through tables are models.** `orm_state_expand` adds, for each
  m2m field, `{"name": "<Owner>_<field>", "table": <through_table>,
  "fields": [id (pk, auto), <from> fk -> Owner, <to> fk -> Target]
  (both `cascade`), "unique_together": [[from, to]]}`. The autodetector
  expands both sides, so through tables are created, dropped and rebuilt
  like any table.
- **`history` follows CREATE_HISTORY / DROP_HISTORY only.**
  CREATE_TABLE always leaves it false (and the autodetector writes
  `"history": false` into CREATE_TABLE model_json).

| Op | State effect |
| --- | --- |
| CREATE_TABLE | append the model_json model; `op.table` overrides its table |
| DROP_TABLE | remove the model |
| RENAME_TABLE | `source_table` model gets table `table` |
| SWAP_TABLES | the two models exchange table names and list positions |
| ADD_COLUMN | append the normalized field_json field (`op.column` wins) |
| DROP_COLUMN | remove the field and every index / unique_together using it |
| ALTER_NULL | set `null` and, when present, `deprecated` from field_json |
| ADD_INDEX / DROP_INDEX | add `{name, fields, columns, unique, condition}` / remove by name |
| ADD_CONSTRAINT | `CHECK (x)` -> `checks` `{name, sql: x}`; `FOREIGN KEY (c) REFERENCES t (pk) ON DELETE a` -> the column becomes an fk to t's model and is also kept in a `constraints` list; `UNIQUE USING INDEX` -> nothing (the unique index is already there); anything else -> `constraints` |
| DROP_CONSTRAINT | remove from `checks`, `constraints` (an FK reverts its column to int) or `indexes` |
| CREATE_HISTORY / DROP_HISTORY | `history` true / false |
| VALIDATE_CONSTRAINT, COPY_COLUMN, COPY_TABLE, SYNC_TRIGGER, DROP_SYNC_TRIGGER, BACKFILL, RAW_SQL | none |

An op that does not fit (unknown table/column/index, duplicate table or
column, unparsable JSON) stops the replay with
`st.error = "<migration>: <OP>: <reason>"`.

## Autodetector rules

Tables match by SQL table name, columns by SQL column name; model and
field names are not compared. Fields without a column (reverse FKs) and
`default`, `enum_values`, `related_name` and the Python-side flags
(`auto_now`, `read_only`, ...) are ignored.

| Difference | Change |
| --- | --- |
| new table (incl. through table) | `create_table` (model_json = model, history off) |
| table gone | `drop_table` (reverse model order, so through tables first) |
| new column | `add_column` (field_json = field with `unique`/`indexed` cleared; `nullable`, `has_default` from the field), plus `add_unique` / `add_index` for those flags |
| column gone | `drop_column` |
| `null` changed | `alter_null` |
| field newly `deprecated` | `alter_null` nullable (field_json carries `"deprecated": true`) |
| `deprecated` removed | `alter_null` to the field's nullability (backfill + tighten when NOT NULL) |
| int column becomes fk | `add_fk`, sql `FOREIGN KEY (c) REFERENCES <table> (<pk>) ON DELETE <action>` |
| new plain index (an `indexes` entry or an `indexed` field) | `add_index` (named from the snapshot, else `<table>_<cols>_idx`) |
| new unique set (unique field, unique index or unique_together) | `add_unique`, name `<table>_<cols>_uniq` |
| new check | `add_check`, name from the snapshot, sql `CHECK (<sql>)` |
| named index gone | `drop_index` (U2.2 kind) |
| history on / off | `add_history` / `drop_history` (U2.2 kinds) |
| hint `table.old->new` | `rename_column` (field_json = new field, so a type change rides along) |
| hint `old->new` | `rename_table` (model_json = new model) |
| type, length, precision or pk changed; fk removed or retargeted (on_delete compared as SQL, so protect = restrict); check removed or changed; unique set removed; unnamed index removed | `rebuild_table` (model_json = new model); the table's other changes are dropped, since the shadow table is created in its new shape |

**Type changes rebuild the table** instead of using the planner's
`alter_type` (field duplication). The duplication pattern leaves the data
in a column named `<column>_new`, but the `.orm` format has no way to
name a field's column, so the next diff would see a different column
forever. A rebuild keeps column names. `ORM_CHANGE_ALTER_TYPE` is never
emitted; a column rename hint with a new type gives the duplication
pattern with the new column's own name.

Renames are never guessed: without a hint a renamed column is an
`add_column` plus `drop_column`. Hint sides may use model or table names
and field or column names. Malformed or unresolvable hints, a hint whose
target table or column already exists, a hint whose old column is still
in the new schema, and a column hint on a table that also needs a rebuild
are errors (`d.error`).

Order of `changes`: create tables, rename tables, per-table changes in
snapshot model order (columns in field order, then indexes, uniques,
checks, or one rebuild), drop columns, drop tables, history, index drops.
The planner keeps that order within each stage.

## makemigrations

- **Initial** (old state has no tables): one migration `<NNNN>_initial`,
  phase expand: CREATE_TABLE for each model in snapshot (FK dependency)
  order, then the through tables, then CREATE_HISTORY for history
  models.
- **Otherwise**: the planner's migrations for the planner kinds, then
  U2.2's kinds numbered after them: `<NNNN>_expand_<table>_history`
  (CREATE_HISTORY with the model); for drop history an empty
  `<NNNN>_expand_<table>_history` plus `<NNNN>_contract_<table>_history`
  (DROP_HISTORY, `requires_applied` = the expand); `<NNNN>_expand_drop_<index>`
  (DROP_INDEX). A rebuilt history table gets `add_history` again (its
  triggers stay on the old table).
- `orm_makemigrations_next` replays the existing migrations, numbers after
  the highest leading number, and depends on the last one. An empty diff
  returns no migrations.

## Writer

`<dir>/m<name>.w` defines `orm_migration* <app>_m<name>()` (bytes outside
`[A-Za-z0-9_]` become `_`) from `orm_migration_new`, `orm_op_new` and
`orm_migration_add` only; `model_json` is spelled with one
`string_append` per field so a review diff shows which field changed.
`<dir>/<app>_migrations.w` imports each module as
`<module_prefix>.m<name>` and returns `<app>_migrations()` in order.
Writing never touches an existing migration module; the index keeps the
entries it already lists (read back from its `l.push(...)` lines) and
appends the new ones. The modules are meant to be committed by app
authors; this repo's tests write under `bin/orm_migrate_writer_out/`.

## Notes for the applier (U2.4)

- CREATE_TABLE model_json holds the whole new table: columns (fields with
  a non-null `column`), inline `unique` / `indexed` / fk flags, `indexes`,
  `checks`, `unique_together`. m2m and reverse fields have no column and
  must be skipped; through tables come as their own CREATE_TABLE.
- ADD_COLUMN field_json never carries `unique` / `indexed` (separate ops)
  but does carry fk `rel_model` / `on_delete` for a new FK column.
- A rebuild's shadow CREATE_TABLE reuses the model's index and constraint
  names, which are schema-global on both dialects; the applier has to
  name the shadow's indexes uniquely (and rename them at SWAP_TABLES).

## Limits

- Default changes (`default`), enum value lists and the ORM-only flags
  produce no migration.
- RAW_SQL is not interpreted by the state.
- Renaming a table that other tables reference rebuilds those tables (the
  FK target changed); their old shadow table still references the old
  table when the rename's DROP_TABLE runs in the same stage, so that drop
  needs CASCADE (PostgreSQL) or a later deploy.
- A rebuild that adds a NOT NULL column without a default relies on the
  copy step to fill it.
- The writer escapes `\`, `"`, newline, CR and tab in literals; other
  control bytes are written raw.
