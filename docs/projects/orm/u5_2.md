# U5.2: example app and end-to-end test

Part of w-orm ([#754](https://github.com/reardan/w/issues/754),
[orm.md](../orm.md)), plan sections 5.3 and 11.3. A small lending-library
app in [`examples/orm/library/`](../../../examples/orm/library/README.md)
that uses every landed layer, and a test that runs it end to end on
SQLite and PostgreSQL across a two-step (expand/contract) migration.

## What landed

| Path | What |
| --- | --- |
| `library.orm` + generated `library_orm*.w`, `library_schema.json` | Release-2 schema: Author, Book (history, enum, decimal, CHECK, FK), Loan (history). |
| `v1/library_v1.orm` + generated modules | Release-1 schema (Book `pages`), the "old code". |
| `migrations/{auth,session,library}/` | Committed migrations from `orm_makemigrations_next` + `orm_write_migrations`: the auth and session tables (U3.1/U3.2 snapshots), library `0001_initial` (release 1) and the rename `0002`-`0005`. |
| `migrations.w` | `library_app_migrations()`, `library_app_migrations_upto(app, n)`. |
| `app.w` | `library_app_new(db)`, `library_app_dispatch(app, req)`, `library_app_mount(app, server)`: three viewsets, `/api/auth/{csrf,login,logout,token}/`, `/openapi.json`. |
| `main.w` | `bin/orm_library migrate|createsuperuser|serve`. |
| `makemigrations.w` | `bin/orm_library_makemigrations [--release1] [--rename hint] [--dry-run]`. |
| `example_cases.w` | The scenario. |

Targets: `orm_example_test` (SQLite file, tests_x64),
`orm_example_postgres_test` (skips without `W_SQL_POSTGRES`) and
`orm_example_postgres_local_test` (temporary cluster through
`bin/sql_postgres_fixture`; skips as root), `orm_example_gen_test`
(regenerates both module sets and `cmp`s them), `orm_example_cli_test`
(the binary's migrate/createsuperuser commands, lint on both dialects),
`orm_library_makemigrations` (builds the tool and dry-runs it: nothing
to plan). The conventional `*_test.w` scan does not cover `examples/`,
so all of them are source-owned (`binary=` / `target=` directives).

## The scenario

Two connections play two processes: release-2 code (the app) and
release-1 code (`v1/` module).

1. Static: every migration lints clean (0 findings) on both dialects;
   replaying release 1's migration gives exactly `library_v1.orm`'s
   tables and columns (autodetector diff empty); the committed rename
   equals what makemigrations plans from release 1 on either dialect;
   makemigrations has nothing left to plan for any app.
2. Release 1 (auth, session, library `0001`): users, a group carrying
   the librarian's model permissions, a reader with `view_book`; session
   login through `/api/auth/csrf/` + `/api/auth/login/` (missing token,
   missing cookie, bad password, key rotation), token login; old code
   writes books; history rows without a user. Applying everything at once
   is refused (contract with its expand in one run).
3. Expand deploy (`0002` + `0003`): old and new code insert and update
   each other's rows through `pages` / `page_count`, pre-existing rows
   were copied, both filters agree, the REST API lists old-code rows.
   Then the API: anonymous vs signed-in querysets, page-number links and
   `page_size`, lookups through relations, search, bad filters (400),
   limit/offset with a pk list; session writes with and without CSRF,
   CHECK/FK/blank/unique errors mapped to fields, model permissions
   (403), admin delete; checkout action (201, 409) and cursor-paged
   loans scoped to the user; history routes with `history_user_id` and
   reason of the request (the loan written by the checkout action carries
   the reader); `/openapi.json` (paths, `page_count` params, security,
   `Book.page_count` and no `pages`). Both releases are checked again.
4. Contract `0004`: new code works; old-code writes no longer sync.
5. Contract `0005` (separate run): `pages` dropped; ORM, REST and history
   still work for new code; release-1 reads fail; status shows nothing
   pending; logout invalidates the cookie.

## Decisions

- **Old code in the same process.** Two generated modules with the same
  model names would clash, so release 1 is `app library_v1` with models
  `AuthorV1` / `BookV1` / `LoanV1` and `table=` on each. The test proves
  it describes the release-1 database (the autodetector compares tables
  and columns, not model names). The committed `0001_initial` was
  planned from that snapshot (`--release1`), so its `model_json` names
  are the `V1` ones; nothing reads model names from migrations except FK
  resolution, which goes through the same `model_json`.
- **A nullable rename.** The rename plan of a NOT NULL column differs per
  dialect (PostgreSQL adds a `CHECK (c IS NOT NULL) NOT VALID` in the
  migrate step); on SQLite that CHECK would reject old-code inserts
  before the AFTER dual-write trigger fills the new column. A nullable
  column plans identically on both, so one committed migration list
  serves both databases (the test asserts it). See the change requests.
- Migrations are planned for PostgreSQL (`ORM_DIALECT_POSTGRES`), the
  stricter plan; the test lints them for both.
- The auth and session tables come from migrations of their snapshots,
  committed in the example, since `libs/standard/orm/auth/` ships none.
- Login, logout, CSRF and token endpoints are plain handlers in front of
  the router (`library_auth_dispatch`): U4.1 has no non-model views.
- The default authenticators (session, then token) are kept, so an
  unauthenticated write is 403 (no challenge), as in DRF.

## Library problems found

- SQLite tables use `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so the
  rowid of the most recently deleted row is reused. With history on, the
  new object's `history/` then also lists the deleted object's rows (the
  test hit it for a book and a loan). PostgreSQL's sequences don't reuse.
- During a SQLite column rename the dual-write trigger fires before the
  history insert trigger, so an insert records a `~` row with a lower
  `history_id` than its `+` row; newest-first lists show an update
  "before" the insert.
- A fresh database can't take the whole list without `force`, because
  contract migrations refuse to run in the same apply run as their
  expand step, and the CLI has no "apply up to <name>".

## Limits

- The NOT NULL rename / NOT NULL add-column patterns are not exercised
  here (dialect-specific plans); U2.4's scenario covers them per dialect.
- No HTML views or admin (U4.3/U5.1); JSON API only.
- `serve` is plain HTTP, single process; throttles are in memory.
