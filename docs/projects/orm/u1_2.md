# U1.2: SQL compiler and dialects

Part of the w-orm plan (issue #754). This unit turns a C3 query tree into SQL
text plus bound values for SQLite and PostgreSQL.

## What landed

- `libs/standard/orm/compile.w`: the compiler.
- `libs/standard/orm/dialect_sqlite.w`, `dialect_postgres.w`: dialect
  singletons with the C5 capability flags, and each dialect's function-name
  spellings.
- `libs/standard/orm/orm_compile_test.w` (`orm_compile_test`): golden SQL and
  bound values for both dialects. The test also runs a sample of the compiled
  statements (multi-row INSERT with RETURNING, select_related, the LIKE/GLOB
  lookups, NOT on a nullable column, aggregates with FILTER and HAVING, a
  correlated subquery, a window function, UPDATE/DELETE through joins,
  upserts and FOR UPDATE SKIP LOCKED) against real tables: SQLite in memory
  always, and PostgreSQL when `W_SQL_POSTGRES` is set. The
  `orm_compile_postgres_local_test` target provides that variable through
  `bin/sql_postgres_fixture` (tests/sql_postgres_fixture.w).

## API

```w
orm_dialect* orm_dialect_sqlite()
orm_dialect* orm_dialect_postgres()
int orm_compile(orm_query* q, orm_dialect* d, orm_compiled* out)  # 1, or 0 + out.error
char* orm_compiled_sql(orm_compiled* c)        # borrowed statement text
char* orm_compiled_param(orm_compiled* c, int i)
int orm_compiled_param_count(orm_compiled* c)
```

Run a compiled statement with `orm_db_execute(db, out.sql)` or with
`sql_query_params(conn, orm_compiled_sql(out), orm_compiled_param_count(out),
sql_builder_values(out.sql))`. `out.columns` is the C4 column map, filled for
SELECT and for RETURNING. The caller owns `out.error`, which
`orm_compiled_free` does not free.

## Decisions

- **Two passes.** A SELECT is emitted once into a scratch builder to find the
  joins it needs, then again into the real builder with the full FROM clause.
  This keeps the walk to a single tree walk with no separate planning step,
  and keeps `?` placeholders in text order. Subqueries run the same two
  passes inside their parent.
- **Aliases.** The outer query uses `t0`, `t1`, ..., the first subquery level
  uses `u0`, ..., the next uses `v0`, and so on. `OUTER_REF` resolves the path
  in the enclosing context, and joins there when the path needs it.
- **Joins.** Each relation path is joined once, keyed by its path prefix, and
  later uses of the path reuse that join. A non-null FK gets an INNER JOIN. A
  nullable FK, a reverse FK or an M2M gets a LEFT JOIN, and once a chain has a
  LEFT JOIN, every later hop is LEFT too. An M2M joins through the through
  table. `author__id` (an FK followed by the target's pk) uses the local
  `author_id` column and needs no join. A relation that ends a path means the
  related model's pk (`tags` = `tags__id`). Multi-valued joins can return
  duplicate rows, as in Django; use `distinct`.
- **Columns.** SELECT skips `ORM_F_DEPRECATED` fields. `only_fields` limits
  the root model's columns and always keeps the pk. Models joined by
  select_related always select all their columns, and their column-map
  entries carry the `rel_path`.
- **Lookups.** `exact`/`ne` with a NULL right side become `IS [NOT] NULL`.
  `in` drops NULL entries, compiles an empty list to `1 = 0`, and accepts an
  `ORM_E_SUBQUERY` in `rhs`. `isnull` treats `0`, `f`, `false`, `False` and
  `""` as false. The text lookups (`iexact`, `regex` and the `contains`,
  `startswith` and `endswith` families) fail on fields that are not
  text-backed. The case-insensitive lookups use `ILIKE` on PostgreSQL and
  `LOWER(x) LIKE LOWER(?)` on SQLite. Every LIKE pattern escapes `%`, `_` and
  `\` and uses `ESCAPE '\'`. `regex` is PostgreSQL-only (`~`).
- **SQLite case-sensitive lookups use GLOB.** This deviates from the
  original plan. SQLite's `LIKE` ignores ASCII case, so on SQLite `contains`,
  `startswith` and `endswith` compile to `GLOB`, with `*`, `?` and `[`
  escaped as `[*]`, `[?]` and `[[]`. PostgreSQL uses `LIKE ... ESCAPE`.
- **exclude() semantics.** `NOT (lookup)` on a nullable column (or through a
  LEFT JOIN) adds `AND col IS NOT NULL` inside the NOT, so rows where the
  column is NULL stay in the result, as in Django.
- **SQLite numeric comparisons.** Values are bound as text, and SQLite only
  converts text through a column's affinity. When the left side is a computed
  number (an aggregate, a window, or an expression with `output_kind`), the
  value is emitted as `CAST(? AS INTEGER|NUMERIC)` on SQLite.
- **Grouping.** An explicit `group_by` is used as given. Otherwise, when the
  select list contains an aggregate (not one inside a window or subquery),
  the query groups by every non-aggregate output column: plain columns by
  name, computed values by ordinal position.
- **Names.** In WHERE, HAVING and GROUP BY, a field path that names an
  annotation or a `values()` entry inlines that expression. In ORDER BY, a
  bare name of this kind orders by the output column (`ORDER BY "n"`).
  ORDER BY also accepts a leading `-` as an alternative to `descending`.
- **Dialect switches.** If a dialect does not support the `FILTER` clause,
  the compiler emits `CASE WHEN` inside the aggregate instead. If it does not
  support `NULLS FIRST/LAST`, it emits a `CASE ... IS NULL` sort key. An
  offset without a limit is `LIMIT -1 OFFSET n` on SQLite. With a LEFT JOIN
  present, `FOR UPDATE` becomes `FOR UPDATE OF "t0"`. Function names are
  mapped per dialect: `GREATEST`/`LEAST` become `MAX`/`MIN` on SQLite,
  `STRING_AGG` and `GROUP_CONCAT` are swapped, and `NOW()` becomes
  `CURRENT_TIMESTAMP`. Function, aggregate and operator names are validated,
  and `ORM_E_INT` must be digits.
- **Writes.** UPDATE and DELETE use bare column names. When their WHERE needs
  a join, it becomes `"pk" IN (SELECT "t0"."pk" FROM ... WHERE ...)`. SET
  values may reference the row's own fields (F expressions) but not related
  paths. A correlated subquery in SET qualifies the outer column with the
  table name. INSERT takes the field order from the first row, accepts later
  rows in any field order, and fails on a missing or extra field. An empty
  single row becomes `DEFAULT VALUES`. ON CONFLICT supports `DO NOTHING` (with
  or without target fields) and `DO UPDATE SET col = excluded.col`. LIMIT and
  OFFSET are rejected on UPDATE and DELETE.

## Limits

- The compiler never splits a statement. Bulk callers must keep the bound
  values per statement under `d.max_params` (999 for SQLite, 65535 for
  PostgreSQL) by batching rows themselves.
- On PostgreSQL, `contains` and the other pattern lookups do not cast
  non-text columns to text.
- `only_fields` does not restrict the columns of models joined by
  select_related.
- Function names must be passed in upper case for the dialect mapping to
  apply.
- The SQLite flags assume SQLite 3.35 or later (RETURNING; FILTER and NULLS
  ordering need 3.30). The emulations cover dialects that clear those flags.
