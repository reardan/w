# U3.3: trigger-based history

Part of w-orm (issue #754, plan section 8). Implements contract C8: history
rows are written by database triggers, so `save()`, queryset `update()`,
`bulk_create` / `bulk_update`, migrations' backfills and raw SQL from any
connection are all captured. Linux x64, SQLite and PostgreSQL.

## What landed

| Path | What |
| --- | --- |
| `libs/standard/orm/history/ddl.w` | History table and trigger DDL: `orm_hist_create` (CREATE_HISTORY), `orm_hist_drop` (DROP_HISTORY) and the hooks that keep history in step with schema changes. |
| `libs/standard/orm/history/history.w` | Runtime API: context, history queries, `as_of`, diff, revert, changeset revert, prune. |

## Table and triggers

`<table>_history`: `history_id` (INTEGER PRIMARY KEY / BIGSERIAL), every
model column except `no_history` fields (same types as the live column,
nullable, no constraints; FK columns included without the FK), then
`history_date` (UTC; SQLite text `YYYY-MM-DD HH:MM:SS.fff`, PostgreSQL
`TIMESTAMP`), `history_type` (`+` `~` `-`), `history_user_id`,
`history_reason`, `history_context_id`. Indexes on `history_date`, the pk
column and `history_context_id`.

- **SQLite**: `w_hist_<table>_ins/_upd/_del` AFTER triggers copy the
  tracked columns from `NEW.`/`OLD.`. The update trigger's `WHEN` compares
  them column by column (`IS NOT`), so a save or update that changes
  nothing writes no row.
- **PostgreSQL**: one AFTER ROW function `w_hist_<table>` projects
  `to_jsonb(NEW/OLD)` onto the history table's row type
  (`jsonb_populate_record`). It names no column, so columns can be added
  or dropped without touching it; untracked columns drop out of the
  projection, and an update whose projection is unchanged is skipped.

CREATE_HISTORY takes the tracked columns from `model_json` (the
autodetector always sets it); without one every live column is tracked.
It is idempotent: when the history table exists it adds missing columns,
aligns PostgreSQL column types with the live table and reinstalls the
triggers. `orm_migrate_sql` prints the DDL like any other op.

## Context (who did it)

```
char* id = orm_history_set_context(db, user_id, c"reason")   # fresh random id, caller frees
orm_history_set_context_id(db, c"req-42", user_id, reason)   # explicit id (request id)
orm_history_clear_context(db)
orm_history_publish(db)                                      # re-send db.history_context
```

The JSON `{"context_id": ..., "user_id": N|null, "reason": ...|null}` is
kept in `orm_db.history_context` (C8) and published:

- **PostgreSQL**: `SELECT set_config('w_orm.context', $1, is_local)`;
  `is_local` is true while a transaction is open (`db.atomic_depth > 0`),
  so the context ends with that transaction, and false otherwise (session
  wide until cleared or changed).
- **SQLite**: the one row of the TEMP table `_w_orm_context`. Main-schema
  triggers cannot read TEMP tables (SQLite reports `no such table
  main._w_orm_context`), so publishing also installs, per history table, a
  TEMP trigger `w_hist_ctx_<history table>` (AFTER INSERT ON main.<h>) that
  copies the context row into each new history row. Other connections
  have neither, so their writes are recorded with NULL context.
  Publishing again after migrations create history tables in the same
  connection installs the missing TEMP triggers.

`user_id <= 0` and a null reason are stored as NULL. Writes with no
context still get history rows.

## Reading, diff, revert, prune

```
orm_result* r = Book_history(db, book)          # orm_history_of: every version, newest first
for orm_history_entry* e in orm_history_entries(r): Book_history_row(e).title
orm_result* r = orm_history_for(db, Book_desc(), pk)
orm_result* r = orm_history_context_rows(db, Book_desc(), ctx)   # one changeset, oldest first
orm_result* past = Book_as_of(db, c"2026-10-19 12:00:00")       # Book rows alive then
list[orm_history_change*] d = orm_history_diff(older, newer)    # field, old_value, new_value; orm_history_diff_free
orm_history_revert(db, e)                       # object back to e's state (re-created if deleted)
int n = orm_history_revert_changeset(db, ctx)   # objects reverted, -1 on error
int n = Book_prune_history(db, c"2026-01-01 00:00:00")   # rows deleted
```

- Entries (`orm_history_entry`: model, history_id, date, type, user_id /
  user_isnull, reason, context_id, `row`) live in the `orm_result`;
  `orm_result_free` frees them. `row` is a model row with the tracked
  columns as they were.
- `as_of(t)`: per primary key the newest history row with
  `history_date <= t`, unless it is a delete; the result's rows are model
  rows in pk order.
- `diff` compares the tracked fields (pk excluded) as database text; with
  `older = 0` every non-NULL field counts as changed.
- `revert` copies the tracked columns from the history row inside the
  database (`UPDATE .. SET c = (SELECT c FROM h WHERE history_id = N)`, or
  `INSERT .. SELECT` when the object is gone), so types never round-trip
  through text. It is an ordinary write: the triggers record it under the
  current context.
- `revert_changeset(ctx)`: for every object any registered history model
  wrote under `ctx`, the state before the changeset's first row for it
  (absent when there was none or it was a delete). Deletes run first in
  reverse registry order, then restores in registry order (generated
  modules register in FK dependency order), in one transaction unless one
  is open (`db.atomic_depth > 0`).
- `prune(older_than)` deletes rows with `history_date < older_than`.

Generated API (for each model marked `history`, plus `import
libs.standard.orm.history.history` when any is): `M_history(db, row)`,
`M_as_of(db, when)`, `M_history_row(e)`, `M_prune_history(db, older_than)`.
The schema parser refuses relations (and `related_name`s) with those
names on history models (H1).

## Schema changes keep history in step

The hooks run in the same migration transaction as the change; each is a
no-op when `<table>_history` does not exist.

| Change | SQLite | PostgreSQL |
| --- | --- | --- |
| ADD_COLUMN | history table gets the column (unless `no_history` in field_json), triggers reinstalled with it | history table gets the column; function recreated (drops cached row types) |
| DROP_COLUMN | triggers dropped before (SQLite refuses to drop a column a trigger names), reinstalled after without it | nothing: the function names no column |
| (both) | the history table keeps a dropped column and its old values | same |
| RENAME COLUMN (planner: add new + sync + copy + drop old) | follows from ADD/DROP: the new column is tracked from its ADD_COLUMN, the old one keeps the values from before | same |
| ALTER_NULL / ADD/DROP_CONSTRAINT (12-step rebuild) | the rebuild re-creates the table's triggers from `sqlite_master`, history ones included | in place, nothing to do |
| REBUILD_TABLE (shadow, sync, copy, SWAP_TABLES, drop) | at SWAP_TABLES the triggers (which followed the old rows' table) move to the rebuilt table; the CREATE_HISTORY the autodetector plans after a rebuild adds columns the rebuild introduced | same, plus history column types follow the new table (`ALTER COLUMN .. TYPE .. USING`) |
| RENAME_TABLE | `<old>_history` renamed to `<new>_history`, triggers recreated | same, old function dropped |
| DROP_TABLE | history table kept (history outlives the table) | same |
| DROP_HISTORY | triggers and history table dropped | triggers, function and table dropped |

Writes the shadow table receives during a rebuild come from the sync
triggers and are not recorded; writes to the live table are. On SQLite the
column dual-write of a rename (AFTER triggers) turns one insert into a `+`
row plus a `~` row, in that order: SQLite fires the newest trigger first,
so the history triggers are reinstalled after the sync triggers and a
rebuild recreates them last (H1); and COPY_COLUMN / backfills write `~` rows: they are
real data changes.

## Tests

- `orm_history_sqlite_test` (SQLite file, two connections) and
  `orm_history_postgres_test` / `orm_history_postgres_local_test`: the
  schema from the planned initial migration (its CREATE_HISTORY applies
  unmodified); `save` insert, unchanged save (no row), change; bulk_create,
  bulk_update (only changed rows), queryset `update`, raw SQL with and
  without effect; a second connection with no context; cleared and
  explicit contexts (quotes in the reason); history order, entry fields,
  model rows; diffs; `as_of` before, between and after writes; single-row
  revert and revert of a delete; changeset revert of an insert, two
  updates and a delete; prune.
- `orm_apply_sqlite_test` / `orm_apply_postgres_test` (U2.4's scenario):
  CREATE_HISTORY on `library_book` and `library_author` early, then every
  plan 5.2 change runs with history on: add column, unique, CHECK (SQLite
  rebuild), FK, index, rename column, type change, nullability (rebuild),
  table rebuild with swap, drop column; at the end the history tables hold
  the added and renamed columns, keep the dropped ones, and the swapped
  table's writes are recorded; CREATE_HISTORY again picks up the rebuild's
  new column; unapply drops it; RENAME_TABLE moves a history table along. The makemigrations round trip applies the
  planned migrations unmodified (the CREATE_HISTORY strip is gone) and
  checks history across the autodetector's `library_book` rebuild,
  including the widened VARCHAR on PostgreSQL.

## Limits

- No write-path hook yet: on PostgreSQL a context set inside a transaction
  ends with it; outside one it is session wide until cleared. A
  per-transaction publish needs `orm_atomic` (U2.1) to call
  `orm_history_publish` after its outermost BEGIN (requested).
- SQLite TEMP context triggers exist only for history tables present when
  the context was published.
- `revert_changeset` overwrites later writes of other contexts to the same
  objects; it reverts only models registered in this program with
  `history` set. M2M through tables have no history.
- `as_of` times are compared as text on SQLite: pass UTC
  `YYYY-MM-DD HH:MM:SS[.fff]`.
- Pruning makes `as_of` before the cut-off incomplete.
- PostgreSQL history type changes cast old values (`USING col::type`); a
  type change whose old history values do not cast fails the migration.
