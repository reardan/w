# U2.4: migration applier, DDL, CLI

Part of w-orm (issue #754, plan sections 5.1 to 5.3). Consumes contract C7
(`orm_op`, `orm_migration`), the U1.1 snapshot JSON and the U2.3 planner and
linter. Linux x64 (the SQL client), SQLite and PostgreSQL.

## API

```
orm_db* db = orm_migrate_open_sqlite(path, &err)     # PRAGMA foreign_keys=ON
orm_db* db = orm_migrate_open_postgres(conninfo, &err)
int n = orm_migrate_apply(db, migrations, force)      # applied count, -1 + orm_db_error(db)
char* sql = orm_migrate_sql(db, migrations, name)     # name 0 = every pending one
char* text = orm_migrate_status(db, migrations)       # "[X] app.name (applied ..., run N)" / "[ ] ..." / "[?] ..."
int ok = orm_migrate_unapply(db, migration)
orm_backfill_register(c"library_book_isbn_backfill", fn)  # int fn(orm_db* db, int batch_size)
return orm_cli_main(argc, argv, migrations)           # in the app's main
```

`orm_migrations(id, app, name, applied_at, run)`, unique on `(app, name)`.
`run` numbers apply calls, which is how "applied in an earlier deploy" is
checked.

`orm_migrate_apply`, before running anything:

- lints every pending migration with `orm_lint_migration`; any error
  refuses the whole run unless `force` (the message carries
  `orm_lint_format` output);
- refuses an op with `unsafe = 1` unless `force` (the linter downgrades
  those to warnings, the applier still wants the explicit override);
- `requires_applied`: the named migration must be recorded by an earlier
  run. If it is earlier in this same run the apply refuses unless `force`;
  if it is nowhere, it refuses even with `force`;
- every dependency must be recorded or earlier in the list.

Then it takes `pg_advisory_lock(754754)` on PostgreSQL and runs each
pending migration in list order. Atomic: one transaction for ops, deferred
statements and the record row. Non-atomic: each ordinary op in its own
transaction, `non_atomic` ops (CONCURRENTLY, batched copies, backfills)
outside one, the record last. A failure stops the run, rolls back the
current transaction and leaves that migration unrecorded; re-running
resumes (index builds use `IF NOT EXISTS`, an INVALID leftover concurrent
index is dropped first, copies skip rows already copied).

`orm_migrate_sql` runs the same code in collect mode: catalog lookups still
read the live database (so a SQLite rebuild prints the real new table), DDL
is appended to the text. Batched copies print one statement with
`:last`/`:upper` keyset bounds, backfills a comment.

Backfills: the applier calls the function until it returns 0; each call
does one batch and returns the rows it changed (negative = error, message
via `orm_db_set_error`). Outside an atomic migration each call is its own
transaction.

`orm_migrate_unapply` inverts one recorded migration in one transaction:
RAW_SQL runs `reverse_sql`; CREATE_TABLE, ADD_COLUMN, ADD_INDEX,
ADD_CONSTRAINT and SYNC_TRIGGER are dropped; copies, backfills and
validation are no-ops; anything else refuses.

## DDL per op

| Op | SQLite | PostgreSQL |
| --- | --- | --- |
| CREATE_TABLE | from `model_json`: types below, `INTEGER PRIMARY KEY` for an auto int pk, NOT NULL, UNIQUE, DEFAULT, enum `CHECK (c IN (...))`, bool `CHECK (c IN (0, 1))`, FK `REFERENCES t (pk) ON DELETE ...`, model CHECKs, `unique_together` constraints, declared and `indexed` indexes, M2M through table (`id` pk, both FKs `ON DELETE CASCADE`, `UNIQUE (from, to)`, index on `to`) created at the end of the migration | same, `BIGSERIAL PRIMARY KEY` |
| DROP_TABLE | `DROP TABLE` | `DROP TABLE .. CASCADE` (a rebuilt table's old shadow may still reference a renamed table, u2_2.md) |
| ADD_COLUMN | `ADD COLUMN`; UNIQUE becomes a unique index | `ADD COLUMN` |
| DROP_COLUMN | drops plain indexes covering it, then `DROP COLUMN` | `DROP COLUMN` |
| ALTER_NULL | 12-step rebuild (skipped when already in the target state) | `ALTER COLUMN SET/DROP NOT NULL` |
| ADD_INDEX / DROP_INDEX | plain | `CONCURRENTLY` when `non_atomic` |
| ADD_CONSTRAINT | CHECK / FOREIGN KEY: rebuild with the constraint appended (rows are checked by the copy and `foreign_key_check`); `UNIQUE (..)`: unique index; `UNIQUE USING INDEX`: no-op | `ADD CONSTRAINT ... NOT VALID` for CHECK / FOREIGN KEY |
| VALIDATE_CONSTRAINT | no-op | `VALIDATE CONSTRAINT` |
| DROP_CONSTRAINT | rebuild without it, or `DROP INDEX` | `DROP CONSTRAINT IF EXISTS` |
| COPY_COLUMN | `UPDATE .. SET new = old WHERE new IS NULL` per pk window | same with `CAST(old AS <new type>)` |
| COPY_TABLE | `INSERT .. SELECT common columns .. WHERE NOT EXISTS` per pk window | same |
| SYNC_TRIGGER (columns) | AFTER INSERT / UPDATE OF triggers with `WHEN` guards; a NOT NULL old column without default is relaxed first (see limits) | one BEFORE INSERT OR UPDATE PL/pgSQL trigger, casts to each column's type |
| SYNC_TRIGGER (tables) | AFTER INSERT/UPDATE/DELETE triggers both ways, `NOT EXISTS` / `IS NOT` guards | AFTER ROW triggers both ways, guarded by the transaction-local setting `w_orm.syncing`; the new table's pk default is switched to the old table's sequence |
| DROP_SYNC_TRIGGER | drops the triggers | drops triggers and functions; table pairs get their own sequences back, moved past `MAX(pk)` |
| SWAP_TABLES | drops sync triggers, three renames with `legacy_alter_table=ON` (other tables' FKs keep the name), then index names swap prefixes (drop + recreate) | drops sync triggers, three renames, FKs from other tables to the old table are re-added against the name `NOT VALID`, index names (and so their unique / pk constraints) swap prefixes with `ALTER INDEX .. RENAME` |
| RENAME_TABLE | rename with `legacy_alter_table=OFF` (FKs follow) | `RENAME TO` |
| BACKFILL | registered W function | same |
| RAW_SQL | split at top-level `;` (quotes, comments, `$tag$` bodies) | same |
| CREATE/DROP_HISTORY | history table + triggers (U3.3, `history/ddl.w`) | same |

Types: INT `INTEGER`; BIGINT and FK `INTEGER` / `BIGINT`; BOOL `INTEGER` /
`BOOLEAN`; TEXT and ENUM `VARCHAR(n)` or `TEXT`; DECIMAL `NUMERIC(d, p)`;
DATETIME `TEXT` / `TIMESTAMP`; DATE `TEXT` / `DATE`; UUID `TEXT` / `UUID`;
JSON `TEXT` / `JSONB`; FLOAT `REAL` / `DOUBLE PRECISION`. `kind` may be the
ORM_* number or its name (`"text"`). FK and M2M targets resolve through
`rel_table`, then every `model_json` in the migration list, then the
runtime registry.

DATETIME is `TIMESTAMP` (without time zone) on PostgreSQL on purpose, not
Django's `timestamptz`: contract C2 stores datetimes as naive UTC text
("YYYY-MM-DD HH:MM:SS[.ffffff]"), and `timestamptz` would render them in
the session's TimeZone with a `+00` suffix, so the text would not round
trip unless every connection pinned `TimeZone=UTC`. Switching later is an
ALTER TYPE (`USING col AT TIME ZONE 'UTC'`) through the rebuild pattern.

Tables of other apps' snapshots apply too: `orm_makemigrations` on
`libs/standard/orm/auth/auth_schema.json` (U3.1) creates all seven auth
tables (through tables included) on SQLite and PostgreSQL.

SQLite transactions from the applier run with `PRAGMA foreign_keys=OFF`
(required by the rebuild; the pragma is a no-op inside a transaction) and
`legacy_alter_table=ON`; `PRAGMA foreign_key_check` must be empty before
COMMIT, then both pragmas are restored.

When `CREATE_TABLE` targets a shadow table (`op.table` differs from the
snapshot's table), index names move to it
(`library_author_created_idx` -> `library_author__new_created_idx`;
unique_together constraints are named after the table anyway) and no
through tables are created. SWAP_TABLES moves the names back, so after a
rebuild the live table carries the snapshot's index names again.

M2M through tables: a model's m2m field creates its through table only
when no CREATE_TABLE in the migration list creates that table itself
(U2.2's state models through tables as tables and emits their own
CREATE_TABLE). Model names resolve to tables through every model_json in
the list, first seen first, then overwritten in apply order (recorded
migrations replayed, pending ones as they run), so after a rename an FK
to the model points at its new table.

SQLite `foreign_key_check` rows whose parent table no longer exists are
ignored (what PostgreSQL's DROP TABLE .. CASCADE leaves: the old shadow of
a rebuilt table that still names a dropped table); any other violation
fails the migration.

## Tests

`orm_apply_sqlite_test`, `orm_apply_postgres_test` (+ `_local_test`) run
`orm_apply_scenario.w`: the initial schema from `library_schema_json()`
(checks: enum, CHECK, FK, unique, m2m uniqueness, cascades), the printed
SQL, status, idempotent re-apply; lint refusal (`W-ORM-M002`), force,
`unapply` with `reverse_sql`; refusal of an unsafe forced drop; a failing
backfill; CREATE_HISTORY on the library tables; then one planner change per 5.2 row, each
migration deployed separately with old- and new-code SQL in between:
add NOT NULL column (backfill), add unique, add CHECK, add FK, add index,
rename column, change type, nullable and back to NOT NULL, rebuild table
(swap, FKs and cascades still work, ids don't collide), drop column
(`requires_applied` refusal when expand and contract ship together),
create, rename (both tables written by both versions) and drop table.
Both tests then run `run_makemigrations_roundtrip` on an empty database
(SQLite: a second `:memory:`; PostgreSQL: schema `w_roundtrip`): the
initial migration `orm_makemigrations` plans for the library snapshot,
a title length change (U2.2 plans a table rebuild of `library_book`,
referenced by the through table), and a hinted rename of `library_tag`
(referenced by the through table, so it is rebuilt too and the old tag
table is dropped while the old through shadow still references it); every
migration lints clean and deploys separately, data, FKs, cascades and
index names survive, and a final makemigrations plans nothing.
CREATE_HISTORY applies as planned there (U3.3).
`orm_cli_test` drives `bin/orm` (lint on both dialects, status, sql,
apply twice, usage error).

## Limits

- SQLite column dual-write cannot fill a NOT NULL column before the
  constraint check (AFTER triggers only), so `SYNC_TRIGGER` drops NOT NULL
  on the old column (rebuild) for the transition. The planner's contract
  step marks it deprecated/nullable anyway.
- SQLite `DROP_COLUMN` of a column in a UNIQUE / PRIMARY KEY / CHECK / FK
  constraint fails (SQLite refuses; no rebuild fallback yet). Adding a NOT
  NULL column without default, or with a non-constant default, fails on
  SQLite (SQLite's own rules).
- FK actions (ON DELETE CASCADE) do not fire inside SQLite migrations
  (foreign keys are off); orphans are caught by `foreign_key_check`.
- PostgreSQL swap re-adds FKs `NOT VALID`; validate them later if needed.
  Self-referencing FKs of the swapped tables are not re-pointed.
- Through tables are created after the migration's other ops; FK cycles
  between new tables on PostgreSQL are not ordered.
- `run`/requires checks compare against recorded rows only; there is no
  "N later migrations in between" knob (plan 5.2 "configurable").
- SQLite has no advisory lock; its write lock serializes transactions only.
- Generated trigger/function names longer than 63 bytes are shortened
  with a hash suffix.
