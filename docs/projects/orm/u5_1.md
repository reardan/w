# U5.1: admin

Part of w-orm ([#754](https://github.com/reardan/w/issues/754),
[orm.md](../orm.md)), plan section 9. A Django-style admin mounted on a
U4.3 router and served by its middleware (request db and transaction,
session, auth, CSRF). Forms are U4.3 `orm_form`s over U3.4 serializers,
permissions are U3.1's, history is U3.3's.

## API

```w
orm_admin_site* site = orm_admin_site_new()      # site.title = "W administration"
orm_admin_register(site, Book_desc()).list_display(c"title,author,status,price").search_fields(c"title,author__name").list_filter(c"status,author").ordering(c"title").readonly_fields(c"published_at").per_page(25)
orm_admin_register(site, Author_desc()).display(c"name")
orm_admin_mount(site, router, c"/admin/")         # include under the prefix, namespace "admin"
if (orm_admin_site_error(site) != 0): ...         # also orm_router_error(router)
```

Options on `orm_model_admin` (comma separated lists; each returns the
model admin): `list_display` (field paths, FKs followed with `__`; empty
= the row label), `search_fields` (text paths, `?q=`), `list_filter`
(BOOL, ENUM, FK fields), `ordering` (default `-<pk>`), `readonly_fields`
(shown, never written), `per_page` (100), `display(field)` (the row's
label, Django's `__str__`; default the first of name / title / username /
label / slug, else `<Model> object (<pk>)`), `serializer(ser)` (forms use
it: its read-only / excluded fields and validators apply), `app_label`
(default: the table prefix). `orm_admin_site_templates(site, dir)` loads
templates from another directory; the default
`libs/standard/orm/admin/templates` is relative to the working directory.

URLs under the prefix: `""` index, `login/`, `logout/` (POST),
`<app>/<model>/` changelist, `add/`, `<pk>/change/`, `<pk>/delete/`,
`<pk>/history/`, `<pk>/history/<history_id>/` (GET the version, POST
revert to it).

## Behaviour

- **Gate.** Every view but login needs an active staff user; anyone else
  is redirected to `login/?next=<path>` (Django's `admin_view`; the login
  page tells a logged-in non-staff user so). Then the model permission
  through U3.1 `user_has_perm`: view (or change) for the changelist,
  detail and history; add; change (POST on the change page, revert);
  delete. Missing permission is 403. Active superusers pass without a
  query. Login accepts only active staff users; `?next=` must be a local
  path (`//host` falls back to the index).
- **Index** lists, per app, the models the user may view or add to.
- **Changelist** builds one queryset: `select_related` for every FK the
  columns cross, U3.4 `orm_filter_set` (search `q`, ordering `o`, filters
  by field name) and the page-number paginator (`p`, 1-based). A page is
  a fixed number of statements whatever its size: BEGIN, session, user,
  COUNT, the page, one per FK filter, COMMIT (7 for the test's Book admin;
  asserted for 10 and 5 rows and after adding rows). Bad filter values
  render the messages with status 400; out-of-range pages are 404.
  Column headers toggle `o=<path>` / `o=-<path>`; filter and header links
  keep the other parameters and drop the page.
- **Add / change** use `orm_form_from_serializer(ma.ser)` with FK
  `<select>`s labelled by the target's display field. Valid POSTs save
  and redirect to the changelist (`_continue`: back to the object);
  invalid ones re-render with the serializer's messages; integrity
  errors map to fields (U3.4). Without the change permission the page is
  a read-only detail of every column.
- **Delete** shows Django's confirmation: a tree of the row and every row
  cascading from it (one query per FK level, any depth), a summary per
  model and the M2M link rows that go with them. PROTECT / RESTRICT rows
  and registered models in the cascade the user may not delete block the
  delete (listed; POST is 403). The database performs the cascade (the
  FKs are `ON DELETE CASCADE`).
- **History** (models with `history`): the versions of `<pk>` newest
  first with date, action, user and reason (one query for the users),
  each version's values and its diff from the previous version, and
  revert (`orm_history_revert`), which needs change, plus add when the
  object is currently deleted, so deleted objects can be restored.
- **History context.** Each admin write (add, change, delete, revert)
  runs between `orm_history_set_context(db, user.id, reason)` and
  `orm_history_clear_context`: reasons are `Added.`, `Changed title and
  price.` (fields whose value changed), `Deleted.`, `Reverted to version
  N.`; cascaded deletes carry the same context. The context is cleared
  afterwards so a pooled connection never carries it into another
  request (on PostgreSQL it is transaction-local anyway).
- Everything user-supplied goes through the autoescaping templates; the
  delete tree is built in code with `orm_html_escape`.

## Decisions

- Its own template engine (not the app's), so the admin works next to any
  app templates; context comes from `orm_web_context` (user, CSRF).
- URLs are built from the stored prefix rather than `{% url %}`, since
  the model routes are generic (`<slug:app>/<slug:model>/...`).
- Logout is POST only (Django 5); the header carries a logout form.
- Change messages use field names in form order, Django style.

## Limits

- No M2M widgets (forms cover column fields, as U4.3's), no inlines,
  actions, date hierarchy or `list_editable`; filters only for BOOL,
  ENUM and FK fields; FK columns sort by the FK id.
- No messages framework, so no "added successfully" banners.
- The delete preview reads registered models only (`orm_registry_models`);
  SET_NULL / SET_DEFAULT / DO_NOTHING relations are not listed.
- Search, filters and ordering only through fields the options name;
  no full result count next to a filtered count.
