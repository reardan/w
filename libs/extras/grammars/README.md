# grammars

Grammars for common languages other than W/C, written in the
ParserGenerator `.pg` DSL (`tools/parser_generator.w` +
`libs/extras/parser_generator/`), which compiles a grammar into one
hand-recursive-descent parser module (no runtime beyond
`libs.extras.parser_generator.runtime`). See
`tests/parser_generator/{w,c,sample}.pg` for the DSL itself and worked
examples.

## Layout

- `javascript.pg` — an explicitly adapted grammar with stateful lexical goals,
  template modes, and Unicode-aware matchers. See
  [JavaScript APIs, examples, and compatibility boundaries](../../../docs/projects/javascript.md).
- `sql.pg`, `json.pg`, `csv.pg`, `abnf.pg`, `dot.pg`, `graphql.pg` —
  grammar sources. `sql.pg` is hand-written; the others are
  machine-translated from ANTLR4 by `tools/antlr_to_pg.w` (see
  `antlr_to_pg/README.md`), with each translation's `<name>.pg.report`
  next to it. `./wbuild grammars_refresh` regenerates `json`/`csv` from
  the vendored ANTLR grammars; `abnf`/`dot`/`graphql` come from a local
  `grammars-v4` checkout via `bin/antlr_to_pg`, and `dot.pg` carries one
  hand adjustment on top (its `stmt` rule order).
- `matchers.w` — custom lexer matchers the grammars share (`csv_text`).
- `<name>_matchers.w` — per-grammar matchers generated by
  `antlr_to_pg --matchers`.
- `antlr_to_pg/` — the ANTLR4-to-pg translator's modules, its own
  grammars (`antlr4.pg`, `pg.pg`), vendored test inputs and the
  grammars-v4 sweep; the CLI entry point is `tools/antlr_to_pg.w`.
- `tests/grammars/<name>_demo.w` — one demo/test per grammar, on the
  shared harness `tests/grammars/grammar_demo.w`.

## Building and testing

```sh
./wbuild grammars_sql_test      # also grammars_{json,csv,abnf,dot,graphql}_test
./wbuild antlr_to_pg_test       # translator golden test (json/csv outputs)
```

A demo target compiles the ParserGenerator once
(`grammars_parser_generator` → `bin/parser_generator_grammars`),
generates `bin/generated_grammars_<name>_parser.w` from `<name>.pg`, and
compiles `tests/grammars/<name>_demo.w`, which imports `matchers.w`, the
grammar's `<name>_matchers.w` and that generated parser ahead of the
harness, then runs sample inputs that should parse cleanly and ones that
should be rejected. All of these targets are in `./wbuild tests`.

To use a grammar from your own program, generate its parser the same way
and import `libs.extras.grammars.matchers` (plus `<name>_matchers`
when the grammar has one) before the generated module.

## What `sql.pg` covers

For an importable parser with document ownership, diagnostics, AST traversal,
and a parameterized query builder, see
[SQL parsing and query construction](../../../docs/projects/sql_parsing.md).
The runnable example is `examples/sql/parse_and_build.w` (`./wbuild sql_parse_example`).

A syntax-only common subset (this grammar validates shape, not semantics
— it doesn't know that `FOREIGN KEY` needs a matching table, for
instance):

- `SELECT` — joins (`INNER`/`LEFT [OUTER]`/`RIGHT [OUTER]`/`FULL
  [OUTER]`/`CROSS`/comma), `WHERE`, `GROUP BY`/`HAVING`, `ORDER BY`
  (`ASC`/`DESC`, `NULLS FIRST`/`LAST`), `LIMIT`/`OFFSET`,
  `UNION`/`INTERSECT`/`EXCEPT`, subqueries in `FROM`/`WHERE`/scalar
  position, `CASE WHEN`, `CAST`, aggregate/scalar function calls
- `INSERT INTO ... VALUES (...), (...)` and `INSERT INTO ... SELECT ...`
- `UPDATE ... SET ... WHERE ...`
- `DELETE FROM ... WHERE ...`
- `CREATE TABLE` (column constraints: `PRIMARY KEY`, `NOT NULL`,
  `UNIQUE`, `DEFAULT`, `REFERENCES`, `CHECK`; table-level constraints
  too), `CREATE [UNIQUE] INDEX`, `CREATE VIEW ... AS SELECT ...`
- `DROP TABLE|INDEX|VIEW [IF EXISTS]`, `ALTER TABLE`
  (`ADD [COLUMN]`/`DROP COLUMN`/`RENAME [COLUMN] ... TO ...`)
- Expressions with standard precedence (`OR` < `AND` < `NOT` <
  comparison/`IS`/`IN`/`BETWEEN`/`LIKE` < `||` < `+ -` < `* / %` <
  unary), parenthesized subexpressions, `'...'` string and numeric
  literals, `"..."` quoted identifiers

Rule shapes are loosely modeled on the ANTLR4 `grammars-v4` SQL grammars
(SQLite's in particular, for statement structure), adapted to this DSL's
constraints: no left recursion (precedence is precedence-climbing via a
chain of `*_expr`/`*_tail` rules, same pattern as `c.pg`'s expression
grammar) and no parenthesized groups within an alternative (optional/list
fragments are pulled into their own `rule ... = X | ` — trailing empty
alternative — the same pattern `w.pg`/`c.pg` use throughout).

## Known limitations / next steps

- Keywords match ASCII case-insensitively via inline token matchers, preserving
  the original spelling. Longer names such as `selectivity` stay identifiers.
- `--` line comments, `/* ... */` comments, SQL `''` string escaping, and `""`
  quoted-identifier escaping are supported. String/identifier matchers require
  closing quotes; the document API also diagnoses unterminated block comments.
- Decimal/exponent numbers and `?`, `?1`, `$1`, `:1`, `:name` parameters are
  supported. Parameter binding and schema validation are outside the parser.
- Statements require semicolon separators; the final semicolon is optional.
- No window functions (`OVER (...)`), CTEs (`WITH`), or dialect-specific
  extensions (T-SQL `[bracket]` identifiers, MySQL `` `backtick` ``
  identifiers, PostgreSQL `::type` casts, upserts).

## Future grammars

SQL is the first hand-written grammar; JSON/CSV/ABNF/DOT/GraphQL are
machine-translated demos (see `tools/README.md`). The grammars-v4 sweep
now compiles ~189/288 end-to-end with generated matchers — pick another
green grammar with an `examples/` dir and add `<lang>.pg` plus
`tests/grammars/<lang>_demo.w` (copy an existing demo's `# wbuild:`
header) following this layout.
